# The path package

- Every read and write goes through Payload's own database API (`payload.db`, always with `req`), except the write of the documents below a moved or deleted document: `src/database/branch.ts` picks the statements of the package's own for the site's database, a bulk write in `branch-mongodb.ts` or SQL in `branch-sql.ts`. They store the path and ancestors `findBranchMove` built for each row by the one rule, so no statement holds that rule, a chunk of rows at a time, so what one statement binds stays the same however big the branch is. The SQL is built with the `sql` of the adapter's own drizzle, which `getSql` in `branch-sql.ts` takes from the where of a query, so a site passes nothing and the package has no drizzle of its own and none that can differ from Payload's, and it reads a collection's table off `payload.db.rawRelations`. On Postgres with transactions `findBranchMove` first holds the branch through `lockBranch`, the document's own row and then the rows below top-down, so two saves in one branch wait for each other and neither is ended. Nothing else holds SQL or code per database, and there is no entry per database: one import for the server, `@payloadpack/path`, and one for the admin panel's components, `@payloadpack/path/client`, which the server entry never imports.
- The root of `src` holds only the package's entries, `index.ts` and `client.ts`, and everything else sits in a folder named for its role, where an import names the file, never a barrel. One file per field in `src/fields`, which also puts what a site sets on the field together with the plugin's own; one file per React component in `src/components`, each a client component; one file per Payload hook in `src/hooks`, named for the hook, each with one exported function per entry the plugin adds to that hook's list, whose name says what it does and ends with the hook's name, next to the request context and what `onPathsChanged` hears; the three functions a site calls that read or write documents in `src/api`; what a save takes its slugs from, what makes a path, and what gives the documents below a moved document theirs, in `src/path`; everything that can refuse a save in `src/validation`, one check per file; every read and write of the database in `src/database`, documents in one file, their versions in another, and the statements that write a branch in `branch.ts` with one file per kind of database beside it; small helpers that know nothing about paths in `src/utils`; every message the package shows in `src/plugin/messages.ts`.
- A file is named for what it holds, so nobody opens it to find out, and a function starts with whichever verb says what it does, such as `strip`, `list`, `parse`, `pick`, `merge` or `split`, or `to` for a conversion; the verbs aren't a list to choose from. Four keep one meaning each, so a reader knows the cost at a glance: `find` asks the database, `set` stores in it, `get` reads what is already in memory or the config, and `build` puts something together from its parts, such as a field's config, and is never used for a function that changes, cuts, checks or converts what it is given. No name invents a word for something that has a plain one: a document's path and ancestors are called that.
- The rule that makes a document's path and ancestors lives in `src/path/build-path-and-ancestors.ts` only, which never asks the database. A hook never works out a path itself, and never predicts what Payload will write: it looks at what the database holds after the write. The one thing the check before the write knows of it is whether Payload writes the document itself, from the status and from the `draft` an update or a restore was sent with, which `beforeOperation` notes.
- Which collections get a path is known in `src/plugin/options.ts` only: `getPathCollections` takes the ones listed in the plugin's `collections` and the ones wrapped in `withPath`, which keeps their options in the collection's server-only `custom` under `withPath`. `pathPlugin()` keeps what it resolved in the config's `custom` under `pathPlugin`, and `getPathCollectionSlugs` gives a site the slugs from there. Nothing after `getPathCollections` knows which way a collection was given.
- `pathRelationshipField` in `src/fields/path-relationship.ts` gives a site's relationship field an empty `relationTo` and keeps the `relationTo` it was given, if any, in its `custom` under `pathRelationshipField`. `pathPlugin()` lists those fields with Payload's `traverseFields` in every list of fields the config it gets holds outside a field, and `fillPathRelationshipFields` sets their `relationTo` in place: to the list the field was given, once it has checked that each of them has a path, or else to the slugs `getPathCollectionSlugs` gives. It never touches another relationship field, and decides by the `custom`, never by the field's own `relationTo`, which the first build of a config fills.
- Where a collection's parent comes from is known in `src/plugin/options.ts` only: `getParentFieldName` names the plugin's own `parent`, the parent field of Payload's hierarchy, or none for a collection given with `parent: false`. No other code names a parent field, a collection without one is never asked for `ancestors`, and there is no code per way beyond that. The plugin sets nothing on a site's `hierarchy`.
- Whether a collection is localized is known in `src/plugin/options.ts` only: `resolveCollection` decides it, from the site's localization and the collection's `localized: true`, and `isLocalized` answers it. In memory a document's paths hold one per locale of the site in every collection, and in one that isn't localized every locale holds the same path. Only what reads a slug or a path off a row, writes one to a row or names one in a query asks `isLocalized`. No other code checks the site's localization for it, and nothing reads it off the shape of a value.
- Whether a row holds a status per locale is Payload's own answer per collection, not the site's: one per locale where the collection has a localized field, and one for every locale where it has none. `getPublishedLocales` in `src/utils/published-locales.ts` asks the running config.
- A row's parent agrees with its ancestors. `buildPathAndAncestorsFields` in `src/database/documents.ts` is the one function that turns a path and ancestors into what a row stores, and it holds the parent they hang from where the row holds another one. A write of a whole row and the statements of a move both store what it returns, so a move has one write for every row below.
- Tests never mock Payload, the database or the package's own modules. Each test runs on MongoDB, Postgres and SQLite, without and with localization, against databases the tests start themselves.
- The speed tests hold one promise: `findByPath` runs one query per collection on the path index, and none for a path with a reserved segment. And a rename, a move and a delete run the same statements with 30 documents below as with 3. What a save costs beyond that is not pinned.
- A pull request that changes the package's `src` gets the query report, `test/query-report.ts`, which CI's Query report workflow runs on the base and on the pull request in turns and comments with what a lookup, a publish and a move cost: their queries, exactly, and their median times.
- After a change to what a lookup, save or move costs, run `bun run bench` in `packages/path` (about an hour, mostly seeding). Only that full run writes its numbers, with what they ran on, to `apps/docs/src/data/path-speed.json`, which the speed page renders, and to the table between the `speed-table` markers in `packages/path/README.md`; a run with fewer documents or databases, or with `BENCH_COMPARISON=off`, only prints them. Never edit either by hand.
- `apps/docs/src/data/path-remote-server.json` holds each way to build paths timed against a MongoDB server on another machine, which the speed page renders. No command writes it: `bun run bench` runs its databases on the same machine.
- A message on a docs page under `apps/docs/src/content/docs/path` is copied word for word from `packages/path/src/plugin/messages.ts`. A change to a message changes its page in the same commit.
- The demo shows the three ways a collection gets its parent: pages by the plugin's own parent, posts without one, and topics by Payload's hierarchy. Topics are also its collection that isn't localized, so its seed gives them no Swedish slugs, the one with an option on its slug field: an access that lets no save in Swedish change the slug, and the one wrapped in `withPath`, where pages and posts are listed in `collections`. Every document has a `related` field made with `pathRelationshipField`, and the seed links the About page to a post and a topic, which the site page lists at their paths. It seeds a fresh MongoDB replica set in memory on each start. Its e2e tests run on one production build, without and with localization in the same run, and pass `?locale=en` explicitly, because the admin remembers an editor's last locale.
