# Path limits

What the package can't promise, each with why, what it leaves and what puts it right. Most come from one choice: every read and write but one goes through Payload's own database API, which has no lock, and no write of one field where the write holds a localized value on Postgres and SQLite, or is of a version on MongoDB. The one write that doesn't is of the documents below a moved or deleted document, by statements of the package's own. Read this before promising more in the docs, and before weighing a write path of the package's own against it. A limit the owner has decided says so. Ask him about the others before building on them.

The docs page `apps/docs/src/content/docs/path/limits.md` holds the ones a site would notice and a test has shown, each as what you see, when it happens and what to do, with nothing of how the plugin works. A limit that rests on reading the code stays here only. A change to a limit here changes that page in the same commit.

That API does take a condition on a write: `updateOne` without an `id`, and `updateVersion`, take a `where`. The package uses it for the document row a run of `backfillPaths` writes, through `setPathAndAncestors` with `ifUnchanged`, and `payload-database-api.test.ts` pins what it builds on. A move writes no row through that API: its statements store the path, the ancestors and the parent alone. A probe on all three databases, without and with localization, on Payload 4.0.0-beta.10, found this. A write of a document with `where: { and: [{ id }, { updatedAt }] }` lands while the row is as it was read. After a save since the read it returns `null` and leaves every value as that save wrote it, localized values, arrays, blocks and relationships too, and it doesn't bring back a row whose delete was committed before the write began. On Postgres it also returns `null` when the other change commits while the write waits for the row. No test could make a write wait on MongoDB or SQLite, so there it rests on the write being one statement. For a version, `updateVersion` with only a `where`, the form Payload's types allow, makes a new version on Postgres and SQLite each time it is called. With an `id` beside the `where`, which the types forbid and both adapters read, it lands and refuses as a document's does. So a version row is still written by its `id`. The condition costs two more statements per document written so on Postgres and SQLite, and none on MongoDB, counted on one move with three documents below, when a move still wrote each row so. Not tried: without transactions on Postgres and SQLite, a save that lands between the statements of one write, of which only the first carries the condition. The package's own writes keep a row's `updatedAt`, so the condition tells a save from the read and not two writes of the package, and two saves in the same millisecond look like one. A row whose `updatedAt` Payload didn't write, as an import may leave on SQLite or MongoDB, is not found by the condition, and a row in a collection with `timestamps: false` has none: both are written by their `id`, as every row was before. On MongoDB such a row may hold text that is no date as its `createdAt` or `updatedAt`, which Payload reads and can save and the adapter refuses in a write, so the write leaves that timestamp as the row holds it, and `backfill.test.ts` pins it. On SQLite a probe showed that Payload can't read such a row at all. Decided by the owner: built for document rows.

## Two requests at once

- **A rename saved below a move that is under way leaves a stale path.** A move reads its branch, builds the path and ancestors of every row from what it read, and stores them with a few statements. They write the path, the ancestors and the parent alone, so every other value a save of a document below wrote in between is kept. A save that gives a document below a new slug or parent between the move's read of the branch and those statements is another matter: the statements store the path the move built from the row it read, with the old slug, in that document and the documents below it. They stay there until that document's next save or a run of `backfillPaths`. Reproduced on Postgres without transactions, by holding a row so the move waits: a page below renamed to `tropics` meanwhile ended at `/world/south`, and the page below it at `/world/south/coast`. No test pins it. On Postgres with transactions the move holds its branch before it reads it, so such a save waits for the move. Not decided by the owner.
- **A delete in the moment a backfill writes a row is undone on Postgres and SQLite.** A write of a whole row there is an insert that updates the row when it is there, so it inserts the row again when it is gone. Reproduced through Payload on Postgres with transactions on, when a move still wrote each row so: a document below is deleted in a transaction that commits while the write waits for its row, and the document is back without its versions. Deleting it again works. On SQLite it rests on reading the adapter: the write finds the row's id in one statement and inserts in the next, and a probe showed that a write by `id` inserts a row that is gone. That write serves each document `backfillPaths` writes. A move's statements are updates, which leave a row that is gone as gone. The condition on the write doesn't stop it, as the same test showed with the condition in place: it is on the update, and the row is gone, so the insert goes through. It does leave a row alone whose delete was committed before the write began. Only an update that is not an insert would close it, which Payload's database API doesn't have for a row with ancestors. Not decided by the owner.
- **A save of a latest version between a backfill's read of it and its write of it is lost.** A move's statements write the path, the ancestors and the parent alone, so they keep such a save: tested on Postgres without transactions, by a change committed while the move waits to write the row. A backfill is another matter: the adapters need a whole row for a write through Payload's database API, so it reads each row again right before it writes it. A document's row is then written only while it is as it was read, so a save of the document in between is kept and the backfill takes the row again, tested the same way. A latest version is written by its `id`, so a save of that same version in between, such as an autosave, is written over, which no test has tried. With transactions on Postgres it didn't happen through Payload for a document right below: its save and the save of the document above waited for each other, in either order. Why they wait was not confirmed. A draft save of a document that was never published writes the row and keeps its `updatedAt`, so the condition doesn't see it and a move in that moment writes the old slug's path back: a review reproduced it on SQLite and MongoDB. Not decided by the owner.
- **Two saves of the same path in the same instant can both pass.** Each save checks the path before it writes. Both documents stay at it, `findByPath` returns one of them, and `backfillPaths` lists both. The docs page Limits says so, and `paths.mdx` links there. Saves that run at once on one shared request, outside a bulk update, are two saves in the same instant too. A collection of the plugin's own that holds every taken path in a unique field would close it. Decided by the owner: dropped after it was tried. It is a second copy of every path, which each publish, move, lift and delete has to keep in step, and without transactions a move that stops halfway leaves it out of step, so it refuses saves that should pass.
- **`onPathsChanged` names each document with the path the move built for it.** What the site hears is built from the move's read of the branch, so a document a save gave a new slug or parent meanwhile is named with the path the move stored, which its next save or a backfill replaces.
- **A publish in one locale leaves the row without the paths of the locales the document isn't published in, for a moment.** When Payload publishes one locale it keeps only the locales the document was published in before (`buildLocalizedPublishData` in Payload's `versions`), and the plugin's hook after the write stores the other paths again. A page keeps its path wherever it is published, so `findByPath` still finds it. In between, the path of a locale the document isn't published in takes nothing. With transactions nobody else sees it. Without them a save that fails in between leaves the row so, and `backfillPaths` puts it right. Not decided by the owner.

## Bulk updates and bulk deletes

- **A bulk update refuses a document and goes on.** Payload runs its documents at once and keeps what the others wrote. The plugin never tries a refused document again. Decided by the owner: a refused document is fine, a document left broken or locked is not.
- **The second document of a bulk update at one path is refused even when the first is refused too.** The first takes the path before it asks the database, and may then be refused for a reason of its own. Decided by the owner, as above.
- **A bulk update shows a refusal as Payload's own line.** Such as "The following field is invalid: slug", without the plugin's message, because Payload lists a refused document by one line of its own.
- **A bulk operation inside a bulk operation of the same collection, on the same request, shares nothing with the outer one.** A site hook that starts one replaces what the outer one kept, so from then on the outer one's documents take nothing from each other, and a bulk delete's lifts are no longer one at a time.
- **A bulk delete of a document and one below it reports each delete on its own, in either order.** Payload starts the work after the deletes at once. Each report names where a lifted document ended up, and a document lifted and then deleted in the same bulk delete is named by both: with where it was lifted to, and as gone. The docs say so in `on-paths-changed.md`. The owner has not confirmed this shape.
- **A refusal by a hook added after the plugin's last one comes after the lift.** The lift runs after the site's own `beforeDelete` hooks, so a site hook that refuses a delete refuses it before anything is lifted. A plugin registered later can add a hook behind the lift. With transactions its refusal undoes the lift. Without them the documents below stay lifted.
- **A restored version inside a bulk update isn't tested.** A document saved by an operation by id while a bulk update of its collection runs on the same request takes nothing and is not held to what the bulk update took. For `restoreVersion` that rests on reading the code only.

## A refusal after the write

- **An unpublish and a restored version are refused before the write.** `beforeChange` isn't told whether a save is a draft save: Payload gives a draft save and an unpublish the same `_status`. `beforeOperation` is given `draft`, so the plugin notes there, for an update by id or in bulk and for a restore, whether Payload writes the document itself, and the check before the write uses it. Decided by the owner for the unpublish; the restore came from a review that showed it refused after the write.
- **Without transactions, any refusal after the write leaves the write.** `requirements.md` says a refusal comes before anything is written. That holds for everything the hook before the write can see: a missing slug, a parent, a taken path, a landing of the branch. What only Payload's write decides is checked after it.
- **Without transactions, a delete that fails halfway through its lift leaves a document lifted and its latest version not.** `backfillPaths` puts the document right, which `backfill.test.ts` pins, and leaves the version, which then reads as a pending move back, as a probe showed.

## Localization

- **Adding or removing `localized: true` on a collection that has documents is a migration the site writes.** The plugin doesn't copy the slugs, and doesn't notice when they haven't been copied. The docs say so in `languages.mdx`.
- **In a localized collection without drafts, a locale keeps the slug it fell back to as its own.** A locale has a path only with a slug of its own there, so a later rename of the slug it fell back to no longer moves it.

## Tests

- **Two tests force an order with a timer.** The site hook in the two bulk delete tests of `deletes.test.ts` holds a document for 500 ms, so on a slow enough machine they can pass without having forced the order.
- **Holding a row is Postgres's.** The tests of a save during a move or a backfill run on Postgres only, because no other database lets a test make a write wait. Each asserts that a write waited for the held row, so a move that never waits fails them.
