# Path limits

What the package can't promise, each with why, what it leaves and what puts it right. Most come from one choice: every read and write but one goes through Payload's own database API, which has no lock, and no write of one field where the write holds a localized value on Postgres and SQLite, or is of a version on MongoDB. The one write that doesn't is of the documents below a moved or deleted document, by statements of the package's own, and the limits those bring have a section of their own. Read this before promising more in the docs, and before weighing a write path of the package's own against it. A limit the owner has decided says so. Ask him about the others before building on them.

The docs page `apps/docs/src/content/docs/path/limits.md` holds the ones a site would notice and a test has shown, each as what you see, when it happens and what to do, with nothing of how the plugin works. A limit that rests on reading the code stays here only. A change to a limit here changes that page in the same commit.

That API does take a condition on a write: `updateOne` without an `id`, and `updateVersion`, take a `where`. The package uses it for the document row a run of `backfillPaths` writes, and for a row below a move or a lift that is written by itself because the statements can't give it the path and ancestors its slug and parent make, through `setPathAndAncestors` with `ifUnchanged`, and `payload-database-api.test.ts` pins what it builds on. A probe on all three databases, without and with localization, on Payload 4.0.0-beta.10, found this. A write of a document with `where: { and: [{ id }, { updatedAt }] }` lands while the row is as it was read. After a save since the read it returns `null` and leaves every value as that save wrote it, localized values, arrays, blocks and relationships too, and it doesn't bring back a row whose delete was committed before the write began. On Postgres it also returns `null` when the other change commits while the write waits for the row. No test could make a write wait on MongoDB or SQLite, so there it rests on the write being one statement. For a version, `updateVersion` with only a `where`, the form Payload's types allow, makes a new version on Postgres and SQLite each time it is called. With an `id` beside the `where`, which the types forbid and both adapters read, it lands and refuses as a document's does. So a version row is still written by its `id`. The condition costs two more statements per document written so on Postgres and SQLite, and none on MongoDB, counted on one move with three documents below before the statements of the package's own took over the rows below. Not tried: without transactions on Postgres and SQLite, a save that lands between the statements of one write, of which only the first carries the condition. The package's own writes keep a row's `updatedAt`, so the condition tells a save from the read and not two writes of the package, and two saves in the same millisecond look like one. A row whose `updatedAt` Payload didn't write, as an import may leave on SQLite or MongoDB, is not found by the condition, and a row in a collection with `timestamps: false` has none: both are written by their `id`, as every row was before. On MongoDB such a row may hold text that is no date as its `createdAt` or `updatedAt`, which Payload reads and can save and the adapter refuses in a write, so the write leaves that timestamp as the row holds it, and `moves.test.ts` pins it. On SQLite a probe showed that Payload can't read such a row at all. Decided by the owner: built for document rows.

## Two requests at once

- **A rename saved below a move that is under way leaves a stale path.** A move of a big branch takes a while. Its statements write the path, the ancestors and, on a lift, the parent alone, of each row as it is when they get to it, so a save of a document below between the move's read and the statements is kept. A save that read its parent's path before the statements and writes after them still builds its path from the parent's old one, and the move doesn't read it again. A row the move writes by itself is another matter. A save that gives such a document a new slug or parent, after the move read the branch and before the move wrote that document's parent, builds its path from the parent's old path. The move then finds the row changed and leaves it, with the documents below it. The document stays at a path below where its parent was, until a run of `backfillPaths`. Reproduced once while the fix was built, on Postgres without transactions, by holding a row so the move waits. No test pins it, and it wasn't tried with transactions on. Before the move read each row again it lost that save instead, and left the document with two latest versions. Not decided by the owner.
- **A delete in the moment a move writes a row is undone on Postgres and SQLite.** A write there is an insert that updates the row when it is there, so it inserts the row again when it is gone. Reproduced through Payload on Postgres with transactions on: a document below is deleted in a transaction that commits while the move waits to write its row, and the document is back without its versions. Deleting it again works. On SQLite it rests on reading the adapter: the write finds the row's id in one statement and inserts in the next, and a probe showed that a write by `id` inserts a row that is gone. The same write serves each row a lift writes by itself, and each document `backfillPaths` writes. The condition on the write doesn't stop it, as the same test showed with the condition in place: it is on the update, and the row is gone, so the insert goes through. It does leave a row alone whose delete was committed before the write began. Only an update that is not an insert would close it, which Payload's database API doesn't have for a row with ancestors. Not decided by the owner.
- **A save of a latest version between a move's read of it and its write of it is lost.** A move's statements write the path, the ancestors and, on a lift, the parent alone, of each row as it is when they get to it, so they keep such a save. A row the move writes by itself is another matter: the adapters need a whole row for a write, so `moveBranch` reads each such row again right before it writes it. A document's row is then written only while it is as it was read, so a save of the document in between is kept and the move takes the row again: tested on Postgres without transactions, by a change committed while the move, or the backfill, waits to write the row. A latest version is written by its `id`, so a save of that same version in between, such as an autosave, is written over, which no test has tried. The same holds for each document `backfillPaths` writes. With transactions on Postgres it didn't happen through Payload for a document right below: its save and the save of the document above waited for each other, in either order. Why they wait was not confirmed. A draft save of a document that was never published writes the row and keeps its `updatedAt`, so the condition doesn't see it and a move in that moment writes the old slug's path back: a review reproduced it on SQLite and MongoDB. Not decided by the owner.
- **Two saves of the same path in the same instant can both pass.** Each save checks the path before it writes. Both documents stay at it, `findByPath` returns one of them, and `backfillPaths` lists both. The docs say so in `paths.mdx`. Saves that run at once on one shared request, outside a bulk update, are two saves in the same instant too. A collection of the plugin's own that holds every taken path in a unique field would close it. Decided by the owner: dropped after it was tried. It is a second copy of every path, which each publish, move, lift and delete has to keep in step, and without transactions a move that stops halfway leaves it out of step, so it refuses saves that should pass.
- **`onPathsChanged` can name a document the move left.** What the site hears is built from the move's first read of the branch, so a document a save changed meanwhile is still named with the path the move meant for it: one the move wrote by itself and left, and one whose new slug or parent the statements kept.
- **A publish in one locale leaves the row without the paths of the locales the document isn't published in, for a moment.** When Payload publishes one locale it keeps only the locales the document was published in before (`buildLocalizedPublishData` in Payload's `versions`), and the plugin's hook after the write stores the other paths again. A page keeps its path wherever it is published, so `findByPath` still finds it. In between, the path of a locale the document isn't published in takes nothing. With transactions nobody else sees it. Without them a save that fails in between leaves the row so, and `backfillPaths` puts it right. Not decided by the owner.

## The statements of a move

A move, a rename and a lift write the documents below with statements of the package's own (`src/database/branch.ts`). They find a row by the moved document among its ancestors, as the row is when they run. None of these is decided by the owner, and none has a test: each rests on a review that read the code, unless it says otherwise.

- **On Postgres and SQLite without transactions, a save between the statements that write the ancestors leaves a document's ancestors mixed.** The ancestors of the rows below are rows of the table of relationships, and a move to another parent or a lift writes them in three statements: the old ones move on, the new ones go in, and the old ones up to the moved document come out. A save of a document below that lands between two of them writes that document's ancestors whole, and the statements after it then add to them or take from them. The document is left with ancestors that are neither the old ones nor the new, until a run of `backfillPaths`. The released code left the same: Payload writes a row's ancestors in a delete and an insert, which two saves at once mix too. A probe on Postgres without transactions, with 50 documents below and both saves started together, 20 rounds a pair, found a wrong row after 48 of 324 rounds on the released code and after 17 of 340 with the statements, and no save ended on either. The second save has to come while the first still runs, which a rename or a move of 1,000 documents below now does for about half a second, where it took 40 to 80. Not tried on SQLite. With transactions the three are one change, and MongoDB writes them in one update per row.
- **On Postgres with transactions, a move holds its branch, and a save that waited for it writes its own document twice.** Two saves in one branch used to end each other there: Payload writes a saved document with `id` among the values it sets, so Postgres holds that row against the foreign key check of every other save that stores the document among its ancestors, and the statements took the rows below in no order. A probe with 50 documents below found one save ended with `deadlock detected` in 16 of 20 rounds for two moves at once, 20 of 20 for two renames, 20 of 20 for a delete with a rename above it, and 4 to 13 of 20 for a save of nothing but a title below a move or a rename, which the released code had too. So before a move, a rename or a lift reads its branch it holds it (`lockBranch`): the document's own row and then every row below, top-down, with a lock that lets a foreign key check through. The same probe then went through 340 rounds, without and with localization and with 1,000 documents below, with no save ended and no row wrong, and `transactions.test.ts` pins both halves: the lock comes before Payload's write, and a waiting move holds no row below the row it waits for. A move that waited for a move above it read its document before it waited, so once it holds the branch `checkPathBeforeChange` reads the document again, and the hook after the write gives the statements the start the rows below have now. `transactions.test.ts` pins that such a move runs the same statements for 30 documents below as for 3. What it leaves: Payload still writes the document itself with the path built before the wait, and the hook after the write stores the right one, so the save that waited runs 3 to 14 statements more than one that didn't, whatever the size of the branch. Decided by the owner: the save that waited must be as fast as any other.
- **The lock is Postgres's, and it orders the saves of one document each.** Without transactions a lock would end with its statement, and no save holds a row while it waits, so none is taken. From reading the code, not tried: two moves at once that each put their document into the other's branch can still end each other, at Payload's own write of the ancestors, and so can a transaction of the site's own that saves several documents of one branch in another order than top-down. A save that only makes a new version of a published document takes no row of the documents, and 80 rounds of one during a rename above went through.
- **A rename below a rename that is under way can leave its documents below at the old path.** A rename's statements find the start of each path as the rename read it. When the statements of a rename of a document above run between that read and the rename's own, they have replaced that start already, so the rename's statements change no path. The documents below stay below where their parent was, and `onPathsChanged` names them with the paths the rename meant for them, until a run of `backfillPaths`. A count of the rows each statement changed, against the rows the move read, would find it.
- **A document created below a move that is under way is moved along unchecked.** The statements write every row that hangs below the moved document when they run, so a document created there after the move read the branch gets its new path too. The move checked the landings of the documents it read, so this one's new path was never checked against a taken path, and `onPathsChanged` doesn't name it.
- **A row that hangs from a document outside the branch gets the new start and the new ancestors unchecked.** Such a row stores the moved document among its ancestors and a parent that isn't below it, as a move that stopped halfway can leave it. The move builds nothing for it and checks no landing, and the statements still find it.
- **A row written by itself has been through the statements first.** A row whose stored path or ancestors the statements can't turn into what its slug and parent make is written by itself after them, read again right before. When that write is skipped, because the row is gone or a save gave it another slug or parent meanwhile, the row keeps what the statements gave it: the new ancestors, on a lift the new parent, and the new start where its path had the old one. Before the statements such a row was left as it was. Either way it is put right by `backfillPaths`.
- **A row written by itself below a document a save renamed during the move gets the path the move built.** The rows below a skipped row are skipped only when the skipped row was written by itself. A row the statements serve is never read again, so when a save renames it during the move, a row below it that is written by itself gets the path the move built from that parent's old slug, until a run of `backfillPaths`.
- **The numbers that order a row's ancestors on Postgres and SQLite have gaps after a move.** The statements leave the ancestors in the right order with numbers that no longer run from 1 without a gap. Payload reads them in order and writes them whole from 1, and a review found nothing in its adapters that needs them without gaps.
- **A database that speaks MongoDB's protocol without update pipelines can't run a move.** The statements on MongoDB are updates with a pipeline.
- **On MongoDB with transactions, two saves in one branch at once lose one of them, and a delete with a rename above it can lose both.** MongoDB doesn't make a transaction wait for a document another one wrote: it ends it with `WriteConflict`, and Payload doesn't try again. A probe with 50 documents below ran each pair 20 times on the released code and with the statements, and no round left a row wrong. The released code lost one save in every round of every pair. With the statements a save of nothing but a title below a move or a rename went through with it in 10 to 15 rounds of 20, two moves and two renames still lost one in every round, and in a localized collection a delete with a rename above it lost both in 6 rounds of 20, where each statement had written a document the other needed. Saving again works. Not decided by the owner.
- **On Postgres and SQLite a site has to pass its adapter's `sql`.** The package builds its SQL with drizzle's `sql` and can't import it itself: a site has one of four SQL adapters or none, a bundler stops at an import of a package the site doesn't have, and Next packs the adapter and drizzle into its own files, so a copy loaded by name when the site runs is a second drizzle, or is missing where only traced files are deployed. A packed install outside the repository showed each of these. Decided by the owner: the site passes it, so the statements are built by the drizzle that runs them, and a site that leaves it out is refused when Payload builds the config.
- **A collection's table is read off the adapter's relationships.** `getTableName` finds it in `payload.db.rawRelations`, under the name the adapter gives a relationship to the collection, its slug and `ID`. That name is the adapter's own and not part of what Payload promises a plugin.

## Bulk updates and bulk deletes

- **A bulk update refuses a document and goes on.** Payload runs its documents at once and keeps what the others wrote. The plugin never tries a refused document again. Decided by the owner: a refused document is fine, a document left broken or locked is not.
- **The second document of a bulk update at one path is refused even when the first is refused too.** The first takes the path before it asks the database, and may then be refused for a reason of its own. Decided by the owner, as above.
- **A bulk update shows a refusal as Payload's own line.** Such as "The following field is invalid: slug", without the plugin's message, because Payload lists a refused document by one line of its own.
- **A bulk operation inside a bulk operation of the same collection, on the same request, shares nothing with the outer one.** A site hook that starts one replaces what the outer one kept, so from then on the outer one's documents take nothing from each other, and a bulk delete's lifts are no longer one at a time.
- **A bulk delete of a document and one below it reports each delete on its own, in either order.** Payload starts the work after the deletes at once. Each report names where a lifted document ended up, and a document lifted and then deleted in the same bulk delete is named by both: with where it was lifted to, and as gone. The docs say so in `on-paths-changed.md`. The owner has not confirmed this shape.
- **A refusal by a hook added after the plugin's last one comes after the lift.** The lift runs after the site's own `beforeDelete` hooks, so a site hook that refuses a delete refuses it before anything is lifted. A plugin registered later can add a hook behind the lift. With transactions its refusal undoes the lift. Without them the documents below stay lifted.
- **A restored version inside a bulk update isn't tested.** A document saved by an operation by id while a bulk update of its collection runs on the same request takes nothing and is not held to what the bulk update took. For `restoreVersion` that rests on reading the code only.

## A refusal after the write

- **An unpublish and a restored version are refused before the write.** `beforeChange` isn't told whether a save is a draft save: Payload gives a draft save and an unpublish the same `_status`. `beforeOperation` is given `draft`, so the plugin notes there, for an update by id or in bulk and for a restore, whether Payload writes the document itself, and the check before the write uses it. Decided by the owner for the unpublish; the restore came from a review that showed it refused after the write.
- **Without transactions, any refusal after the write leaves the write.** `requirements.md` says a refusal comes before anything is written. That holds for everything the hook before the write can see: a missing slug, a parent, a taken path, a landing of the branch. What only Payload's write decides is checked after it.

## Localization

- **Adding or removing `localized: true` on a collection that has documents is a migration the site writes.** The plugin doesn't copy the slugs, and doesn't notice when they haven't been copied. The docs say so in `languages.mdx`.
- **In a localized collection without drafts, a locale keeps the slug it fell back to as its own.** A locale has a path only with a slug of its own there, so a later rename of the slug it fell back to no longer moves it.

## Tests

- **Two tests force an order with a timer.** The site hook in the two bulk delete tests of `deletes.test.ts` holds a document for 500 ms, so on a slow enough machine they can pass without having forced the order.
- **Holding a row is Postgres's.** The tests of a save during a move or a backfill run on Postgres without transactions only, because no other database lets a test make a write wait. Each asserts that a write waited for the held row, so a move that never waits fails them. In a localized setup the test holds the document's row of English in the table of locales too, where a move's statement writes the path. A row held while a move's statements write it is tested for a rename only. For a move to another parent and a lift, `moves.test.ts` holds a row that is written by itself, and no test holds one their statements write.
- **Which ids the statements are proven with.** `moves.test.ts` renames, moves and lifts a branch with uuid ids on Postgres and SQLite and with a collection's own number and text ids on all three, with transactions on Postgres so the lock runs too. Each cast was shown to fail them: the uuid and text cases on Postgres and SQLite, the number case on MongoDB. Number ids on Postgres and SQLite and text ids on MongoDB pass and no broken cast made them fail, since they are stored as the default ids are.
- **A lift that stops between its statements leaves the latest version below the document that was not deleted.** Without transactions, a delete that fails after the lift wrote the parent of a document right below and before it wrote that document's latest version leaves the document lifted and its latest version still below the document whose delete failed. `backfillPaths` gives the document the path and ancestors of where it was lifted to and finds nothing to change in the version, which now reads as a pending move back, so the next publish puts the document below the undeleted one again. `backfill.test.ts` pins what happens to the documents. Not decided by the owner.
