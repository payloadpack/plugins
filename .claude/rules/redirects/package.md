# The redirects package

- The lookup is the design the owner settled, kept exactly: one `payload.find` with `overrideAccess: false` and `depth: 0` for the redirects whose `lookupPath`, the From of a redirect from a path and the fixed start of a regex, is in the path and every path above it, lowercased, and the path and the visitor's query string as a redirect compares it, the same paths as the visitor typed them, but for one that holds a NUL, which Postgres can't compare, and `/`, that are On, sorted by `_order`, selecting only what it reads. A redirect that matched the query string wins, then redirects from the path or a path above it as compared, the deepest first, then regexes, in the editors' order, each compiled once for the lookup and matched against the whole path with RE2JS's `matcher(path).matches()`, never cached. Then only the winner's document target is read, with one `findByID` as the visitor at depth 0: only the fields the site's `documentSelect` names, or the whole document without it, for the site's `buildDocumentPath`, which builds the path from it. A target that gets no path on this site sends nobody and gives way to the next. A path over 2,048 characters or 32 segments gets none, so no lookup reads more than 33 paths. The path it looks up, the one asked for or a destination a chain goes on from, has the slash at its end dropped by `stripEndSlashes`, as a From has, so a site with Next's `trailingSlash` finds the same redirects, and a regex matches the path without it. Change none of it without asking him.
- A From of Exact path and Path and subpaths is stored lowercased and decoded but for what a URL reads as something else or drops (`%`, `?`, `#`, a backslash, a control character, whitespace at the end), which `toComparedPath` keeps encoded as the lookup compares a visitor's path, and Exact path's query string lowercased and decoded but for a control character and for whitespace at the end of a name or value, its parameters sorted by name and then value, without tracking parameters, by `cleanFromPath`, which reads a backslash and an encoded slash as a slash, refuses a value with no path on this site, such as a `mailto:` link, and cleans its own output to itself, as a save sends the stored from back, a save that changes only the status or the order too. A suggestion's From is the old path as `toComparedPath` compares it, which `cleanFromPath` cleans to itself, so a `?` or `#` in a path stays part of it. A regex and its fixed start stay as written. A query string on Path and subpaths, or on a regex (one that holds `\?`, or `?` and a name and `=`), is refused. A From over 2,048 bytes in UTF-8 as it is stored, cleaned or trimmed, also where the admin validates what an editor typed, is refused with the package's own message, so Postgres's unique index on `from`, which holds at most 2,704 bytes a row, can always hold one, and so it has no more characters than the longest path a lookup answers. Every destination keeps the visitor's query string but for the parameters a redirect matched, after the target's own, whose value wins. Without `winOverDocuments`, `findRedirect` never asks `hasDocument` about the path asked for; in no mode does it ask about a destination that is its document target's own path; and it says `matchedQueryString`, so a proxy without `winOverDocuments` lets a page win over any other redirect.
- `findRedirect` resolves to `{ foundRedirect }`, typed `FindRedirectResult`, so a later field can join it. `winOverDocuments` changes only what happens after the lookup's query, which stays one `payload.find` with the same where and order, selecting `winsOverDocument` too only with `'perRedirect'`. Left out, nothing changes. With `'always'`, the best candidate wins and a document never stops it, so `findRedirect` never calls `hasDocument`, and it follows a chain through documents, looking up every destination on the site until none answers. With `'perRedirect'`, the Redirects collection gets the checkbox `winsOverDocument`, labelled Wins over a page, unchecked by default and on a suggestion said yes to; `hasDocument` is required, and `findRedirect` throws without it; at a path the best candidate wins if it matched the query string or is checked, otherwise `hasDocument` is asked once, and where a document holds the path only a candidate that matched the query string or is checked wins, picked from the same candidates in the same order, before its target is read. A chain looks up every destination on the site and applies the same rule there, where a destination that is its document target's own path holds a document without asking. In both modes a chain ends at a destination where no redirect answers, also a path it met, and answers null where a redirect would send visitors on from a path met before with the same query string, or leave an 11th path, so a redirect from a query string back to the bare path asked for goes on there; and a redirect that matched the query string wins over a document. `hasDocument` is asked when the first candidate that can't win over a document comes up before any that answers, so also when that one then sends nobody.
- A regex runs on `re2js` only, its one runtime dependency, pinned exactly. A save refuses a regex RE2 can't compile or whose `programSize()` is over 1,000. `getFixedStart` reads the fixed start off `re2Input.prefix`, which RE2JS doesn't document, so `regex.test.ts` pins the fixed start of each shape of regex.
- The root of `src` holds only the entries, `index.ts` and `client.ts`, and everything else sits in a folder named for its role, where an import names the file, never a barrel: the two functions a site calls in `src/api`, one file per field of the Redirects collection in `src/fields`, the plugin, its collection, its options, the notices' field and their endpoint, and the hook that deletes a deleted document's suggestions, in `src/plugin`, the admin's client components in `src/admin`, and what cleans a path, matches a regex and builds a destination, without the database, in `src/redirect`. `client.ts` is the `./client` export the import map names, built like `@payloadpack/theme`'s with swc beside `tsc` for the types, with `react` and `@payloadcms/ui` as peers, and nothing a client component imports reaches `src/plugin/options.ts` or the database. Every message the package shows is in `src/plugin/messages.ts`, and the docs copy them word for word, in the same commit as a change.
- A function starts with whichever verb says what it does, such as `strip`, `list`, `parse`, `pick`, `merge`, `split`, `clean`, which turns what an editor typed into what is stored, `match`, which runs a regex, or `to` for a conversion; the verbs aren't a list to choose from. Three keep one meaning each, so a reader knows the cost at a glance: `find` asks the database, `get` reads what is already in memory or the config, and `build` puts something together from its parts, such as a field's config or a destination, and is never used for a function that changes, cuts, checks or converts what it is given.
- The package doesn't depend on `@payloadpack/path`. A site gives `collections` and `buildDocumentPath`, which are required, and `documentSelect` itself, the way the docs show for path, and `suggestRedirects` takes what `onPathsChanged` hears by its shape, so neither the code nor the published types import path. Only the tests and the demo use it.
- Every read and write goes through Payload's Local API and passes `req` and `context` on. A lookup reads as its request's user; `suggestRedirects` writes with `overrideAccess: true` through the save's `req`, so its suggestions are in the save's transaction, and its calls on one `req`, which a bulk delete or a bulk update makes at once, run one after another, so Payload's orderable gives each suggestion a place of its own, but for a call from inside a running one, such as from a site's hook on a suggestion it writes, which runs at once rather than wait for itself. A bulk delete deletes every document before any reports, and a page a site doesn't show reports no delete of its own, so on every report of a move `suggestRedirects` first reads which documents of the report are still stored: Postgres and SQLite refuse a relationship to a row that is gone.
- No redirect goes live without a person's yes, and no move suggests one unless the site calls `suggestRedirects`, from its own hook or from `onPathsChanged`, which decides which moves do. A status replaces any switch: On, Off, which answers as if the redirect weren't there, and Suggested, which answers nobody, and the lookup asks for `status` On itself. A move writes a suggestion with status Suggested, never one that is on, and the collection keeps `versions: false`, with no stored state but the status. `suggestRedirects` reads the redirects from the old and new path of each moved branch's top, and from the path of each document published, in one read, then deletes before it writes, so a change that moves several documents, such as two that swap paths, meets none on the unique from: at each of those new paths, of a document of any collection, the suggestions and any redirect to that document, whatever its status, and at each old path an earlier suggestion. It writes none from an old path a redirect that is On or Off holds, nor from one any document of the same change moved to, nor from one over 2,048 bytes, and then each document right below that moved with it gets one by the same rules, after one more read of their old paths. It deletes no redirect that is On or Off but one to the document at its new path. Each collection a redirect can send visitors to gets an `afterDelete` hook, after the site's own, that deletes the suggestions to a document once it is deleted, through the delete's `req`, so a document whose delete fails keeps them all, and leaves one a site's own hook refuses to delete as it is, without failing the document's delete; a redirect to it that is On or Off stays and sends nobody, and a document in the trash keeps its suggestions until it is deleted from there. Each of its reads and deletes names at most 1,000 values, a chunk at a time, since SQLite binds at most 32,766 in one statement.
- Each collection a redirect can send visitors to gets the notices' field first, `redirectSuggestions`, a `ui` field whose client component reads the Redirects collection's endpoint `/suggestions/:documentCollection/:documentId` as the signed-in user, once on load and again whenever `useDocumentInfo().lastUpdateTime` changes, which the edit view sets on every save, since a server-rendered field doesn't render again after a save. Every edit view asks, and a site that never calls `suggestRedirects` has no suggestions, so the endpoint asks for the document's suggestions first, by its document key, and reads the document only when it has one: as the user, drafts included, with its path built by the plugin's `buildDocumentPath`. Yes and No go through the Redirects collection's own REST API with a `where` on the id and status Suggested, so Payload's access decides who answers, and an answer to a notice someone else answered first changes nothing. Edit links to the suggestion in the admin, so an editor changes it before picking On. Each notice is Payload's neutral `Banner`, the kind Payload puts a control in, with its icon centred on the sentence, the sentence in regular text and the buttons below it.
- The Redirects collection shows labels only, without descriptions, with Status and Type in the sidebar. Status offers On and Off, and Match Exact path and Regex. Suggested and Path and subpaths, `SUGGESTED_MATCH`, which only a move writes, show only on a redirect that has them, through each select's `filterOptions`, which Payload runs again on every change in the form, so an editor who picks another option no longer sees them. Match is a select because a radio has no `filterOptions`. Anyone reads the redirects that are On, and only a user of the admin's own collection reads every one, as in Payload's default access. The collection keeps Payload's authorship, `createdBy` and `updatedBy`, hidden as Payload has them, built with Payload's own `createCreatedByField` and `createUpdatedByField` so that only a user of the admin's own collection reads them, which costs a lookup no query: it selects neither, and Payload strips a field the select leaves out before its read access runs.
- Tests never mock Payload, the database or the package's own modules. Every test that needs a database runs once on each setup of `test/support/setups.ts`: MongoDB, Postgres and SQLite with transactions, and SQLite without them, its default, on a MongoDB replica set, an embedded Postgres and a directory of SQLite files the tests start, each site on a database of its own; `REDIRECTS_TEST_DATABASES` narrows them, such as to `sqlite`. A test of what a transaction rolls back runs only with transactions. Every behaviour and edge case of the owner's brief has a test that fails when it breaks.
- The speed tests hold these promises. On MongoDB a lookup's query runs on an index scan of `lookupPath_1` alone, examines at most one key for each value it asks and one more for each redirect it returns, and no document it doesn't return, a save of a new redirect reads one key of `_order_1_createdAt_1` to put it last, and an edit view finds its document's suggestions on `targetDocumentKey_1` alone, reading only the redirects to that document. On SQLite the lookup's plan searches `redirects_lookup_path_idx` alone and never scans the table, also after `ANALYZE`, for mostly redirects from paths, half regexes and only regexes, and a save finds the last redirect from the end of `redirects__order_idx`; the notices' query and a delete's read of a document's suggestions search `redirects_target_document_key_idx` and never scan the table, also after `ANALYZE`, whatever share of redirects sends visitors to a document. Postgres picks its plan by cost, so its tests hold that the indexes on `lookupPath`, `_order` and `targetDocumentKey` exist. On every database a lookup costs one query, the relationship of a document target included, also with a query string and when another candidate sends visitors to a document, and two when the redirect that wins sends visitors to a document; a delete of a document a redirect can send visitors to asks once for its suggestions, on `targetDocumentKey_1` on MongoDB, and no more when it has none; with `winOverDocuments` a lookup costs the same, `'perRedirect'` adds no query beyond the site's own `hasDocument`, which it calls only when the best candidate can't win over a document by itself, and every path on the site a chain lands on costs one lookup more, a document target's own path included; the collection keeps no versions, so an editor's move writes the same suggestion with 1,000 pages below as with 3, a row in `redirects` and, on Postgres and SQLite, one insert into `redirects_rels` for its target and its authorship; and the longest path a lookup takes, 2,048 characters in 32 segments, answers within 5 ms on every database.
- The benchmark is `apps/redirects-bench`, a Next.js app built three times from the same source, each build's page extensions picking its proxy: with `src/proxy.ts`, the proxy the docs give for query strings, with `src/proxy.win-over-documents.ts`, the one they copy for redirects that win over pages, both calling this app's own `findPage`, and without any proxy. The build for redirects that win over pages runs with `winOverDocuments: 'always'`, which adds no field, so every build reads the database the bench seeded. Its numbers are what each proxy adds to a page view no redirect covers: the proxy for query strings with a query string and without one, and the proxy for redirects that win over pages without one, at the most redirects and at both distances. After a change to what a lookup costs, run `bun run bench` there (about 10 minutes): it starts MongoDB, Postgres and SQLite itself, with MongoDB and Postgres also 5 ms away through a relay. Only the full run, all three databases at 1,000, 10,000 and 100,000 redirects, writes its numbers, with what they ran on, to `apps/docs/src/data/redirects-speed.json`, which the speed page renders, and to the tables between the `speed-table` and `speed-table-win-over-documents` markers in the README. Nobody edits either by hand.
- Payload's orderable puts a new redirect last with a sort on `_order` and the adapter's `createdAt`. Payload checks a collection's indexes before orderable adds `_order`, so the collection can't declare an index for that sort; on MongoDB `addIndexes` in `src/plugin/indexes.ts` wraps the adapter's `init` and adds `{ _order: 1, createdAt: 1 }` to the model's schema once the models are built and before it connects, so mongoose builds it with every index Payload declares, under `autoIndex` and the adapter's `ensureIndexes`. SQLite needs no more: it reads Payload's own index on `_order` from its end and sorts only the redirects that share the last `_order`, and Postgres's planner picks the same at 1,000 and at 100,000 redirects. On both, a document target sits in `redirects_rels`, whose column for each collection Payload indexes itself, and on every database a redirect also stores the document key of its target on its own row, in the hidden `targetDocumentKey`, which a hook sets on every save from the stored fields with the sent ones over them, as `lookupPath`'s is, and which Payload indexes alone: an index with the status beside it has Postgres without statistics read it for a lookup's status. The notices' query and a delete ask for status Suggested and that key, sorted by `type`, a field no index holds, since a sort on `from`, on `_order`, Payload's own, or on a field the where fixes, which Payload follows with `createdAt`, has SQLite with statistics read every redirect in the order of an index, and the notices sort the few they find by `from`.
- The demo has pages below pages and news items at `/news` without a parent, with `suggestRedirects` in `pathPlugin()`, and seeds a move, whose suggestion nobody answers, and five redirects that are on, one typed in mixed case and one from a query string, on a fresh MongoDB replica set in memory on each start. It runs without `winOverDocuments` and checks for redirects in both places a site can: its page route for paths no page holds, and `src/proxy.ts` for URLs with a query string, both asking `src/find-page.ts`, which the docs copy word for word, the route on the installation page and the proxy on the page on query strings, each taking `{ foundRedirect }` from `findRedirect`. Its e2e tests cover only what the demo reaches and the package's tests can't: its page route, its proxy, Payload's own reorder endpoint and the admin, and never repeat a lookup the package's tests answer on every database. They ask for paths as a visitor, with a request of no session; a test of a move says yes to its suggestion first, and the notice is tested in the admin, as an editor sees it right after the save that moves a page.
