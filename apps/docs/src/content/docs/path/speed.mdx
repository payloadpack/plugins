The top charts come from a **remote MongoDB server** reached over the internet (6.4 ms per query, 10,000 pages per collection) — the setup most hosted sites run, where extra round trips add up quickly.

## Four ways to give a page its path

| Approach      | Stored fields                 | Finding a page                        | Getting a link's path               |
| ------------- | ----------------------------- | ------------------------------------- | ----------------------------------- |
| path          | Slug, parent, ancestors, path | 1 query                               | Already on the document             |
| slug by slug  | Slug, parent                  | 1 query per segment                   | Walk parents up, per link           |
| built on read | Slug, parent                  | All slugs in 1 query, matched in code | Walk parents up, per level          |
| ancestors     | Slug, parent, ancestors       | 2 queries                             | 1 extra query for all links at once |

`slug by slug` is what a site does without a plugin. `built on read` and `ancestors` are prototypes we built to test alternatives, without this package's rules.

## Moving a branch

<SpeedServer kind="moves" />

- **`path 0.1.1`:** saved each page below through Payload (5 queries per page) — a 1,000-page rename took **5,026 queries and 41 s**.
- **`path` now:** builds the new paths from slugs and ancestors (already checked before the write) and writes 1,000 pages with a few statements — **28 queries and 443 ms**.
- **`built on read` and `ancestors`:** store no path, so a rename writes nothing below — paying for it on every read instead, as shown above.

_Note: `path`'s move ran on 20 November (4.9 ms per query on the same server); the rest ran on 19 November._

## Where the others win

- **Top-level pages:** 1 query either way.
- **Renames:** `built on read` and `ancestors` write nothing below the moved page.
- **Sitemaps:** reading every page once and building paths in code takes 86 ms, vs 68 ms for `path`.
- **Same-machine databases (including SQLite):** sub-millisecond queries mean `slug by slug` takes only 1–3 ms even at 10 segments.

## On the same machine

`bun run bench` runs MongoDB, Postgres, and SQLite locally with 100,000 documents and compares `path` against Payload's nested docs plugin and `slug by slug`.

### What each does

|                     | path                                   | nested docs                                                       | slug by slug         |
| ------------------- | -------------------------------------- | ----------------------------------------------------------------- | -------------------- |
| Find a page by URL  | `findByPath`, 1 query per collection   | Query on unindexed `breadcrumbs.url`, then pick the matching page | 1 query per segment  |
| Move a branch       | A few statements per 1,000 pages below | Full save of every page below                                     | One save of the page |
| Create a new page   | One save                               | Two saves                                                         | One save             |
| Refuse a taken path | Yes, naming the document already there | No                                                                | No                   |

<details>
<summary>How the comparison is set up</summary>

- `nested docs` and `slug by slug` each get a copy of the pages (~2,000, with the same versions and drafts, unlocalized).
- `nested docs` uses its documented setup (`generateURL` joining slugs). Its lookup also matches `slug`, otherwise a top-level page query returns its whole branch.
- On MongoDB, `nested docs`' `parent` has no index, so each save below queries it twice.
- `slug by slug` uses an index on `slug` and `parent` added by the site.
- `findByPath` queries `posts` in parallel too; the other two query `pages` only.

</details>

## Run it yourself

```sh
cd packages/path && bun run bench
```

Starts local databases, seeds them, and runs the [On the same machine](#on-the-same-machine) benchmarks in ~1 hour. A full run updates this page and the package README. The remote server numbers at the top come from separate runs.
