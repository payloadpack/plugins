The numbers at the top of this page come from a MongoDB server on another machine, reached over the internet, at 6.4 ms per query and with 10,000 pages per collection. Most sites reach their database this way, so this is where the differences show.

## Four ways to give a page its path

|               | Stores                        | Finds a page                          | A link's path                        |
| ------------- | ----------------------------- | ------------------------------------- | ------------------------------------ |
| path          | Slug, parent, ancestors, path | 1 query                               | On the document                      |
| slug by slug  | Slug, parent                  | 1 query per segment                   | Read from the pages above, per link  |
| built on read | Slug, parent                  | All slugs in 1 query, matched in code | Read from the pages above, per level |
| ancestors     | Slug, parent, ancestors       | 2 queries                             | 1 more query for all links together  |

Slug by slug is what a site does without a plugin. Built on read and ancestors are prototypes we made to test the idea, without this package's rules.

## Moving a branch

<SpeedServer kind="moves" />

Path 0.1.1 saved each page below through Payload, 5 queries a page. A rename took 5,026 queries and 41 s. Built on read and ancestors store no path, so a rename writes nothing below. They pay for it on every read instead, as the charts above show.

We kept the stored path and changed the write. A save already checks every new path in the branch. So a move builds those paths from the slugs and ancestors, and writes 1,000 pages with a few statements: 28 queries and 443 ms.

Path's own move ran on 20 November, when a query to the same server took 4.9 ms. The rest ran on 19 November.

## Where the others win

- **A top-level page** is one query either way.
- **A rename** writes nothing below in built on read and ancestors.
- **A sitemap** can read every page once and build the paths in code: 86 ms, against 68 ms for path.
- **A database on the same machine**, SQLite included, runs a query in a fraction of a millisecond. There, slug by slug takes 1 to 3 ms at ten segments.

## On the same machine

`bun run bench` runs each database on the same machine as the site, with 100,000 documents, and compares path with Payload's nested docs plugin.

### What each does

|                      | path                                      | nested docs                                                          | slug by slug         |
| -------------------- | ----------------------------------------- | -------------------------------------------------------------------- | -------------------- |
| Find a page by URL   | `findByPath`, 1 query per collection      | A query on `breadcrumbs.url`, which has no index, then pick the page | 1 query per segment  |
| A move               | A few statements per 1,000 pages below    | A full save of each page below                                       | One save of the page |
| A new page           | One save                                  | Two saves                                                            | One save             |
| Refuses a taken path | Yes, and names the document that is there | No                                                                   | No                   |

<details>
<summary>How the comparison is set up</summary>

- Nested docs and slug by slug each get a copy of the pages: about 2,000, with the same versions and drafts, and no localization.
- Nested docs runs as its docs set it up, with `generateURL` joining the slugs. Its lookup also matches the slug. Otherwise a top-level page's query returns its whole branch.
- On MongoDB, nested docs' `parent` has no index, and each save below queries it twice.
- Slug by slug uses an index on slug and parent that the site adds itself.
- `findByPath` looks in posts too, at the same time. The other two look in pages only.

</details>

## Run it yourself

```sh
cd packages/path && bun run bench
```

It starts its own databases, seeds them and prints the numbers under [On the same machine](#on-the-same-machine), in about an hour. That full run writes them to this page and to the package's README.

The numbers from the server on another machine come from separate runs, not from `bun run bench`.
